# 승인 체크리스트 v1

v1 · 2회차 (2026-10-06) — 오늘 바뀐 점
- 테스트: "테스트가 충분하다"를 "새 public 메서드(getter · setter · 생성자 제외)마다 테스트 1개 이상"으로 바꿨다.
- 치명 · 범위: 치명 이슈를 비밀값 노출 · 데이터 손실 · 인증 우회 · SQL 문자열 조립 네 가지로 정했다. 요청과 무관한 변경은 같은 파일 안의 import 정리만 허용한다.
- 컨벤션: 계층 규칙 위반 · 빈 catch · System.out 은 반려, 네이밍은 경고로 나눴다. "충분한가 · 적절한가" 같은 판단형 문장을 모두 예/아니오 문장으로 바꿨다.

AI 가 만든 변경분 · 외주사 PR 을 머지하기 전에 리뷰어가 대조하는 목록이다. 네 기준이 **모두** 충족되어야 승인이다. 하나라도 미충족이면 반려.

## 심각도 정의

- **치명** — 그대로 머지하면 서비스나 데이터에 피해를 줄 수 있는 문제. 1건이라도 있으면 반려.
- **경고** — 지금 고치지 않아도 동작하지만 다음 변경에서 사고가 될 가능성이 있는 문제. 승인 여부는 리뷰어가 판단한다.
- **제안** — 더 나은 방법이 있다는 의견. 승인 · 반려에 영향을 주지 않는다. 목록으로만 남긴다.

이슈 한 건은 심각도 · `파일:줄번호` · 근거 · 수정 방향 네 항목으로 적는다. 근거 줄번호를 댈 수 없는 지적은 "확인 필요"로 따로 둔다.

## 1. 테스트 통과

- [ ] 변경된 모듈의 테스트 명령을 실제로 실행했다(실행하지 않고 통과라고 쓰지 않는다).
- [ ] 실행 결과에 실패 · 오류가 0건이다.
- [ ] 새로 생긴 public 메서드(getter · setter · 생성자 제외)마다 그 메서드를 호출하는 테스트가 1개 이상 있다. 컨트롤러 엔드포인트 메서드도 여기에 들어간다.
- [ ] 기존 테스트를 지우거나 건너뛰게(`skip`, `@Disabled`) 바꾼 곳이 없다.

## 2. 치명 이슈 0건

치명 이슈는 아래 네 가지(비밀값 노출 · SQL 문자열 조립 · 데이터 손실 · 인증 우회)다.

- [ ] 비밀번호 · 토큰 · 키가 코드 · 설정 · 테스트 픽스처에 리터럴로 들어 있지 않다.
- [ ] SQL 을 문자열로 이어 붙여 만드는 곳이 없다(파라미터 바인딩 사용).
- [ ] 데이터를 지우거나 덮어쓰는 코드가 새로 생겼다면 요청에 그 내용이 명시돼 있다.
- [ ] 인증 · 인가 검사를 건너뛰거나 지우거나 우회하는 변경이 없다.

## 3. 요청 범위 이탈 없음

- [ ] 요청 문장이 한 문장으로 확인되었다(없으면 판정하지 않고 먼저 묻는다).
- [ ] 변경 파일 목록의 모든 파일이 요청 문장으로 설명된다.
- [ ] 요청 범위 파일 안에서 요청과 무관한 변경은 import 정리뿐이다.
- [ ] 의존성 추가 · DB 스키마 변경 · 설정 파일 변경이 있다면 요청에 포함돼 있었다.

## 4. 컨벤션 준수

4-2 · 4-3 · 4-4 중 하나라도 "아니오"면 이 기준은 미충족(반려)이다. 4-5 가 "아니오"면 **경고**로 기록하고, 이 기준의 충족 여부에는 반영하지 않는다.

- [ ] 4-1. 팀 `CLAUDE.md` 의 코딩 컨벤션과 금지 사항을 대조했다(`convention-check` Skill 이 있으면 그 결과를 쓴다).
- [ ] 4-2. 컨트롤러에 `*Repository` 타입 필드 · 생성자 파라미터가 없고, 서비스가 다른 도메인의 Repository 를 주입받지 않는다.
- [ ] 4-3. 빈 `catch` 블록이 없다.
- [ ] 4-4. `System.out` · `System.err` · `printStackTrace()` 가 없다.
- [ ] 4-5. 이름이 `CLAUDE.md` 규칙을 따른다(클래스 PascalCase · 메서드/필드 camelCase · 상수 UPPER_SNAKE_CASE · 응답 DTO 변환 메서드는 `from`).

기준 밖에서 **경고로만** 기록하는 항목(충족 여부에 반영하지 않는다):
- 로그만 남기는 `catch`, 인자 없는 `now()`, 와일드카드 import, `console.log` (`convention-check` 결과에 나오면 경고로 옮긴다).
- 이 변경을 적용한 뒤 `vendor-prs/*.patch` 중 `git apply --check` 가 실패하는 파일이 생긴다.

## 판정 형식

첫 줄에 `판정: 승인` 또는 `판정: 반려`. 이어서 네 기준의 충족 · 미충족 표, 그다음 이슈 목록(심각도 · `파일:줄번호` · 근거 · 수정 방향). 코드는 수정하지 않는다.
